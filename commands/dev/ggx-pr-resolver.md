# /ggx-pr-resolver — rebase + resolve comments, one pass, one push

**Usage**:
- `/ggx-pr-resolver <PR# | URL> [--auto]` — single PR
- `/ggx-pr-resolver --batch [--user=@me] [--auto]` — sweep all open PRs, one parallel subagent per PR (fan-out pattern identical to `/resolve-conflict --batch`)

`--auto` auto-approves the `/resolve-pr-comments` strategy table (standing approval — used by /ggx-on-duty). Without it, single mode keeps the normal HITL strategy gate; `--batch` implies `--auto` (a batch cannot prompt).

## Per-PR procedure (the unit both modes run)

1. **Context**: `gh pr view` → number, headRef, baseRef, headSha. Skip MERGED/CLOSED.
2. **Ownership guard**: skip any PR whose `headRefName` is in the caller-passed branch skip-set (primary guard — see Batch mode). Also skip if the PR's ticket carries `dispatcher-port-in-flight` / `dispatcher-dev-in-flight` (secondary, label-based — an in-flight pipeline agent owns that branch; the label can be removed mid-sweep by `/dev:ship`, which is why the skip-set is primary). Concurrent standalone+on-duty resolver runs against the same repo are unsupported — /ggx-on-duty runs at most one batch at a time, so no per-PR mutual exclusion beyond this is needed.
3. **Two-stage gate — mechanical pre-filter, then judge. Never decide "nothing to do" from authorship/recency heuristics alone** (every such heuristic has a blind spot — e.g. `latest author != me` permanently hides any thread we started ourselves under the same account). **CI/check status is NEVER a gate criterion — in either direction**: do not skip a PR because its checks are red (a red check is often CAUSED by being behind/conflicting with base — skipping would mean the conflict never gets resolved), and do not treat green checks as "nothing to do". The only inputs to the gate are `needs_rebase` and open review threads; CI status belongs to the caller's notification layer, not to this worker.
   - **3a. Mechanical pre-filter (pure reads, zero LLM)**: `needs_rebase` = head behind base (`gh api .../compare` / mergeable state); `open_threads` = count of unresolved review threads. `!needs_rebase && open_threads == 0` → SKIP (`up-to-date`), no worktree, no judge. This stays cheap for the common all-clean case.
   - **3b. Judge stage (LLM, reads EVERY unresolved thread in full — content, all replies, authors; still NO worktree)**: classify each open thread:
     - `ACT` — needs work now: an unaddressed request for change, a reviewer follow-up after our reply, a code-review finding (including threads we started ourselves), anything whose substance has not been addressed at current HEAD.
     - `HANDLED` — already addressed: we (or anyone) replied with the fix / the fixing commit is on the branch; thread merely awaits the reviewer clicking resolve. Judge by SUBSTANCE (is the concern addressed at HEAD?), not by who spoke last.
     - `HOLD` — skip for now: questions only the human author can answer, wontfix/design debates in progress, bot annotations, comments about code that no longer exists. These are listed in the report (so the human sees them) and trigger no work BY THEMSELVES. HOLD is **advisory screening only** (it decides whether the PR is worth worktree+tests): once steps 4-7 run — because of a rebase or some OTHER thread's ACT — the resolve-pr-comments classifier is authoritative over EVERY open thread, and a HOLD thread it judges STALE may be auto-resolved (owner decision D13; accepted because resolved threads are reopenable and the human-only HOLDs map to REPLY/DEFER, which stay open).
   - Proceed to worktree (steps 4-7) only if `needs_rebase` or any `ACT` thread exists; otherwise report `{skipped: judged-clean, held: [...]}`.
   - The judge is a SCREENING pass of the same nature as resolve-pr-comments' FIX/REPLY/STALE/DEFER — it exists so we don't pay worktree+tests for PRs with only HANDLED/HOLD threads. Borderline → err toward ACT (the downstream classifier double-checks; a wasted pass beats a silently ignored review comment).
   - In batch mode, 3a runs in the top-level sweep; 3b runs inside the per-PR subagent (so judge calls fan out in parallel and the top-level stays mechanical).
4. **Worktree** (batch-B3 primitive — NOT `/add-worktree`, which is trunk-based, interactive on remote-tracking, and fork-blind): derive `<TICKET-ID>` by grepping `headRefName` for `[A-Z]+-[0-9]+` (fallback: sanitized branch name). Reuse an existing worktree already checked out on `refs/heads/<headRefName>`; else raw `git worktree add ../<TICKET-ID> <headRefName>`; fork PRs: `git worktree add --detach` + `gh pr checkout`. **Non-interactive dirty guard with residue triage**: on a dirty reused worktree, first compute `CHANGED = git -C <path> diff --name-only HEAD` (tracked modifications) and split against the residue allowlist `^(pubspec\.lock|ios/Podfile\.lock|Gemfile\.lock|ios/Flutter/AppFrameworkInfo\.plist)$` (keep in sync with `ggx-dispatcher.md` pre-flight `RESIDUE_RE`; inclusion bar: machine-written AND reproducible from a clean checkout). ALL changed files match → machine residue from an earlier build (e.g. flutter rewrites `AppFrameworkInfo.plist` — caused the 2026-06-05 #488 false needs-human): `git -C <path> stash push --message "ggx-pr-resolver residue auto-stash <UTC>" -- $CHANGED` (labeled, recoverable) and PROCEED. ANY file outside the allowlist → a human's in-progress work: report `needs-human: worktree-dirty` listing the non-residue files, touch nothing (never the HITL `/check-clean` path — this may run unattended). This guard MUST run before the stale-reuse refresh below — the hard reset would silently destroy exactly the human work the guard exists to protect. **Stale-reuse refresh (mandatory)**: `git fetch origin <headRefName>` and reset the worktree to `origin/<headRefName>` before rebasing — a reused worktree's stale remote ref would hand step 7's `--force-with-lease` an OLD lease that silently clobbers commits pushed since our last visit (the lease only protects what we last fetched).
5. **Rebase stage** — run `/resolve-conflict --callee --worktree=<path> --base=<baseRef>` (the callee-side contract built for exactly this step; single mode is HITL — AskUserQuestion-on-doubt deadlocks an unattended background agent — and batch pushes): **rebase onto the PR's `baseRef`** — REBASE-only (owner decision D12; never merge) and never assume trunk (single mode hardcodes `origin/trunk`; release-branch PRs exist) — resolve conflicts with `/resolve-conflict`'s mechanics but **batch-style give-up semantics** (unresolvable or uncertain → auto-abort the rebase, report `needs-human: conflict`, push nothing; NEVER prompt), then tests must be green — a suite that is red AFTER a clean rebase (semantic conflict, or a flaky/pre-existing failure the rebase surfaces) → STOP this PR with `needs-human: tests-failed`, push nothing, leave the rebased worktree as-is for inspection (distinct from step 6's `comment-fix-failed-tests`: that is the comments-stage suite over a dirty worktree, this is the rebase-stage suite over a clean one) — format, commit, **NO push yet**.
6. **Comments stage**: if any `ACT` thread → run the `/resolve-pr-comments` procedure (classify FIX/REPLY/STALE/DEFER, apply fixes, post English replies, combined commit; strategy table auto-approved under `--auto`). Its build-sanity gate (format + check-test) still runs — and is the second abort `--auto` does NOT bypass, by design: check-test fails after FIX edits → STOP this PR with `needs-human: comment-fix-failed-tests`, push NOTHING (not even the rebase commit), leave the worktree dirty for inspection. Under `--auto` the skill also suppresses DEFER promise-replies ("will file a ticket after merge" — nobody in the loop files it; owner decision D16).
7. **Single push — always `--force-with-lease`** (the rebase rewrote history; a plain `git push` would be rejected as non-fast-forward). Ownership (owner decision D14): when the comments stage ran, **resolve-pr-comments' own push step executes the push** with `--force-with-lease` (skill-side support is a construction item) and the resolver pushes nothing itself; if there were no comments to resolve, push the rebase commit yourself (also `--force-with-lease`). Either way the branch is pushed **once** per pass — possibly carrying two commits (rebase + comment-fix). A lease rejection (someone pushed between our fetch and our push) → report `push-failed`, do NOT plain-force, and reset the worktree to `origin/<headRefName>` (discard the local commits) so the next pass re-rebases from remote reality instead of stacking on abandoned local commits.
8. **Report** (one of three exit shapes): `{pr#, skipped: up-to-date}` | `{pr#, skipped: judged-clean, held: [...]}` | `{pr#, rebased: yes/no, comments: {fix, reply, stale, defer}, held: [...], resolvedThreadIds: [], pushedSha | needs-human: conflict | tests-failed | worktree-dirty | comment-fix-failed-tests | push-failed}`. `up-to-date` / `judged-clean` / `pushedSha` are stable field names — callers (e.g. /ggx-on-duty) key off them; do not rename.

## Batch mode

- `gh pr list --state open [--author @me]` → fan out one subagent per PR running the procedure above in that PR's worktree (parallel; subagents touch disjoint branches so no isolation needed beyond the worktrees themselves).
- Aggregate the per-PR reports; list `needs-human` PRs prominently.
- Skip-set: callers may pass a set of **branch names (headRefName)** to exclude — the canonical key (owner decision D11; PR numbers cannot work: chain-in-flight tickets may have no PR yet). E.g. /ggx-on-duty passes the dispatcher chain's claimed branches (E-3). Checked against `headRefName` from `gh pr list` BEFORE spawning the per-PR subagent.

## Why one command instead of two

`/resolve-conflict --batch` and `/resolve-pr-comments` are the same category of work — writers to the same PR branch keeping it healthy. Run separately they need mutual-exclusion bookkeeping and push twice (two CI runs). Chained per-PR: rebase first means comment fixes are authored on top of latest base, one push (possibly two commits), one CI run, zero self-racing. A PR needing both stages runs the local suite twice (rebase stage + the skill's build-sanity gate) — deliberate (owner decision D17): the second run is incremental and the simplicity beats conditional skipping.
