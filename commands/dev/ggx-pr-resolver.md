# /ggx-pr-resolver — rebase + resolve comments, one pass, one push

**Usage**:
- `/ggx-pr-resolver <PR# | URL> [--auto] [--stash-dirty]` — single PR
- `/ggx-pr-resolver --batch [--user=@me] [--auto] [--stash-dirty]` — sweep all open PRs, fanning out the single-PR unit via the **`Workflow` tool** (`workflows/pr-resolver-batch.workflow.js`, GGC-92), one script-spawned level-1 agent per PR — the same fan-out mechanism the dispatcher uses (`workflows/dispatch-fanout.workflow.js`)

`--auto` auto-approves the `/resolve-pr-comments` strategy table (standing approval — used by /ggx-on-duty). Without it, single mode keeps the normal HITL strategy gate; `--batch` implies `--auto` (a batch cannot prompt).

`--stash-dirty` (opt-in escape hatch, V2-D) — when YOU pass it, the dirty-worktree guard auto-stashes even **non-residue** tracked changes (labeled, recoverable via `git stash pop`) instead of reporting `needs-human: worktree-dirty`, so a worktree carrying stale leftover edits doesn't block the sweep. **Never the default** — the guard's whole purpose is protecting unintended WIP; only pass this when you know your worktrees hold nothing precious.

## Per-PR procedure (the unit both modes run)

1. **Context**: `gh pr view` → number, headRef, baseRef, headSha. Skip MERGED/CLOSED.
2. **Ownership guard**: skip any PR whose `headRefName` is in the caller-passed branch skip-set (primary guard — see Batch mode). Also skip if the PR's ticket carries `dispatcher-port-in-flight` / `dispatcher-dev-in-flight` (secondary, label-based — an in-flight pipeline agent owns that branch; the label can be removed mid-sweep by `/dev:ship`, which is why the skip-set is primary). Concurrent standalone+on-duty resolver runs against the same repo are unsupported — /ggx-on-duty runs at most one batch at a time, so no per-PR mutual exclusion beyond this is needed.
3. **Two-stage gate — mechanical pre-filter, then judge. Never decide "nothing to do" from authorship/recency heuristics alone** (every such heuristic has a blind spot — e.g. `latest author != me` permanently hides any thread we started ourselves under the same account). **CI/check status is NEVER a gate criterion — in either direction**: do not skip a PR because its checks are red (a red check is often CAUSED by being behind/conflicting with base — skipping would mean the conflict never gets resolved), and do not treat green checks as "nothing to do". The only inputs to the gate are `needs_rebase` and open review threads; CI status belongs to the caller's notification layer, not to this worker.
   - **3a. Mechanical pre-filter (pure reads, zero LLM)**: `needs_rebase` = head behind base (`gh api .../compare` / mergeable state); `open_threads` = count of unresolved review threads. `!needs_rebase && open_threads == 0` → SKIP (`up-to-date`), no worktree, no judge. This stays cheap for the common all-clean case.
   - **3b. Judge stage (LLM, reads EVERY unresolved thread in full — content, all replies, authors; still NO worktree)**: classify each open thread:
     - `ACT` — needs work now: an unaddressed request for change, a reviewer follow-up after our reply, a code-review finding (including threads we started ourselves), anything whose substance has not been addressed at current HEAD.
     - `HANDLED` — already addressed: we (or anyone) replied with the fix / the fixing commit is on the branch; thread merely awaits the reviewer clicking resolve. Judge by SUBSTANCE (is the concern addressed at HEAD?), not by who spoke last.
     - `HOLD` — skip for now: questions only the human author can answer, wontfix/design debates in progress, bot annotations, comments about code that no longer exists. These are listed in the report (so the human sees them) and trigger no work BY THEMSELVES. HOLD is **advisory screening only** (it decides whether the PR is worth worktree+tests): once steps 4-7 run — because of a rebase or some OTHER thread's ACT — the resolve-pr-comments classifier is authoritative over EVERY open thread, and a HOLD thread it judges STALE may be auto-resolved (owner decision D13; accepted because resolved threads are reopenable and the human-only HOLDs map to REPLY/DEFER, which stay open).
   - Proceed to worktree (steps 4-7) only if `needs_rebase` or any `ACT` thread exists; otherwise report `{skipped: judged-clean, held: [...]}`.
   - The judge is a SCREENING pass of the same nature as resolve-pr-comments' FIX/REPLY/STALE/DEFER — it exists so we don't pay worktree+tests for PRs with only HANDLED/HOLD threads. Borderline → err toward ACT (the downstream classifier double-checks; a wasted pass beats a silently ignored review comment).
   - In batch mode, the cheap mechanical pre-filter (3a) may run in the top-level sweep as part of the pre-spawn filter (P0-2 below) so no worker is spawned for an all-clean PR, while the LLM judge (3b) runs inside the per-PR worker. This is purely a spawn-efficiency optimization, **not a split of the unit**: the worker still runs the full procedure (3a→3b→4–7→push) when invoked standalone, and 3a is idempotent if re-run. It is unrelated to the push — the worker always owns that (step 7).
4. **Worktree** (batch-B3 primitive — NOT `/add-worktree`, which is trunk-based, interactive on remote-tracking, and fork-blind): derive `<TICKET-ID>` by grepping `headRefName` for `[A-Z]+-[0-9]+` (fallback: sanitized branch name). Reuse an existing worktree already checked out on `refs/heads/<headRefName>`; else raw `git worktree add ../<TICKET-ID> <headRefName>`; fork PRs: `git worktree add --detach` + `gh pr checkout`. **Non-interactive dirty guard with residue triage**: on a dirty reused worktree, first compute `CHANGED = git -C <path> diff --name-only HEAD` (tracked modifications) and split against the residue allowlist `^(pubspec\.lock|ios/Podfile\.lock|Gemfile\.lock|ios/Flutter/AppFrameworkInfo\.plist)$` (keep in sync with `ggx-dispatcher.md` pre-flight `RESIDUE_RE`; inclusion bar: machine-written AND reproducible from a clean checkout). ALL changed files match → machine residue from an earlier build (e.g. flutter rewrites `AppFrameworkInfo.plist` — caused the 2026-06-05 #488 false needs-human): `git -C <path> stash push --message "ggx-pr-resolver residue auto-stash <UTC>" -- $CHANGED` (labeled, recoverable) and PROCEED. ANY file outside the allowlist → a human's in-progress work: report `needs-human: worktree-dirty` listing the non-residue files, touch nothing (never the HITL `/check-clean` path — this may run unattended) — **UNLESS `--stash-dirty` was passed (V2-D)**: then stash the non-residue files too (`git -C <path> stash push --message "ggx-pr-resolver --stash-dirty <UTC>" -- $NON_RESIDUE`, labeled + `git stash pop`-recoverable) and PROCEED. This opt-in is the ONLY way non-residue changes are touched; without the flag the guard is inviolable. This guard MUST run before the stale-reuse refresh below — the hard reset would silently destroy exactly the human work the guard exists to protect. **Stale-reuse refresh (mandatory)**: `git fetch origin <headRefName>` and reset the worktree to `origin/<headRefName>` before rebasing — a reused worktree's stale remote ref would hand step 7's `--force-with-lease` an OLD lease that silently clobbers commits pushed since our last visit (the lease only protects what we last fetched).
5. **Rebase stage** — run `/resolve-conflict --callee --worktree=<path> --base=<baseRef>` (the callee-side contract built for exactly this step; single mode is HITL — AskUserQuestion-on-doubt deadlocks an unattended background agent — and batch pushes): **rebase onto the PR's `baseRef`** — REBASE-only (owner decision D12; never merge) and never assume trunk (single mode hardcodes `origin/trunk`; release-branch PRs exist) — resolve conflicts with `/resolve-conflict`'s **auto-assume semantics by DEFAULT** (GGC-15): on a non-trivial conflict the callee makes a documented best-effort assumption about merge intent and proceeds — prefer the project's mandated direction, graft the branch's net-new params/copy/design on top of the base side, lean on the ticket as the source of intent — and records every assumption. **NEVER prompts.** The conservative auto-abort (`needs-human: conflict`, push nothing) survives only as the **fallback tier** — used when the conflict is genuinely ambiguous with no defensible default. Then tests must be green — a suite that is red AFTER the rebase (a Tier-1 assumption that turned out wrong, a semantic conflict, or a flaky/pre-existing failure the rebase surfaces) → STOP this PR with `needs-human: tests-failed`, push nothing, leave the rebased worktree as-is for inspection (distinct from step 6's `comment-fix-failed-tests`: that is the comments-stage suite over a dirty worktree, this is the rebase-stage suite over a clean one) — format, commit, **NO push yet**. The push gate is unchanged by auto-assume: tests green + format clean before any push. The canonical definition of the two tiers + heuristics lives in `resolve-conflict.md` **Callee Mode Step 2**; this is the policy summary, not a second source of truth.
   - **Surface the callee's assumptions ledger (GGC-15).** When the callee returns a non-empty `assumptions` array (Step 6 report shape), document it on the PR's tracker ticket — the canonical channel:
     - **Resolve the ticket** from the PR's branch: `<TICKET-ID>` is the one already derived in step 4 (`headRefName` grepped for `[A-Z]+-[0-9]+`). Resolve `ticket_system` from `<TICKET-ID>` via `_ticket-lib.md`'s "Resolution flow", then post **one** comment via the `save_comment` row of `_ticket-lib.md`'s call table (`mcp__claude_ai_Linear__save_comment` / `mcp__claude_ai_Atlassian_Rovo__addCommentToJiraIssue`) whose body starts with the stable marker `<!-- ggx-pr-resolver-assumptions:v1 pr=<PR#> -->` followed by the rendered ledger (one bullet per assumption: file · region · assumption · heuristic). Idempotency: before posting, list comments and skip if a comment with the same `pr=<PR#>` marker already exists (a re-run of the same pass should not double-post).
     - **PR-comment fallback** — when no `<TICKET-ID>` is resolvable from the PR (branch has no `[A-Z]+-[0-9]+`, or `ticket_system` is unknown): post the same ledger as a **PR comment** instead (`gh pr comment <PR#> --body <ledger>`), with the same stable marker.
     - The same ledger is ALSO carried into the step-8 run report (below) — the report and the ticket/PR comment are the two surfacing channels, both fed from the callee's `assumptions` array.
   - **Tests run in the FOREGROUND and block until they exit (P0-1).** Do NOT `run_in_background`, do NOT arm a `Monitor`, do NOT return control to wait for a notification. **A subagent is a linear procedure; backgrounding belongs only to the top-level orchestrator.** (2026-06-08: 4 of 13 workers backgrounded `flutter test` then "parked" waiting for a monitor — resuming just re-parked. Clean rebases that should be ~40k tokens / <50 tool-uses ballooned to 120–140k tokens / 370–416 tool-uses, and 22 orphan `dart`/`flutter_tester` processes survived "completed" agents.) Acceptance: a clean-rebase worker uses < ~50 tool-uses, emits no "waiting for monitor" message, and leaves no orphan test processes. This same rule is restated at the actual executor — `resolve-conflict.md` Callee Mode Step 3.
   - **Rebase-stage verification uses the STRICT-incremental test path, not the full suite (P1-2 / V2-C).** Invoke `/check-test --fix --no-escalate` (file-level on flutter, module-level on android) — **omit `--all`**. The rebase only moved `base`; the branch's own diff is small, so incremental detection covers it, and the full suite is CI's job. **`--no-escalate` is required**, not optional: without it `/check-test`'s widely-used-file fallback escalates a router/provider/theme touch to the full suite (2026-06-08: a `app_router.dart` touch → full 4379-test suite, ~350s, dominating wall-clock for 2/9 workers) — exactly the cost the incremental path exists to avoid. (Semantic-conflict risk is still covered by the post-rebase incremental run + CI. One worker reported a normally-few-minute suite taking ~33 minutes under full-suite × ~7 sibling worktrees in parallel — strict-incremental + the concurrency cap below both attack that.) Because this gate runs `/check-test`, it inherits the per-repo test profile (GGC-24): the android gradle task is the resolved `test_task` / `test_variant` (e.g. `testStandardStagingUnitTest`, not the nonexistent `testDebugUnitTest`), and `known_flaky_tests` are quarantined out of the `--fix` budget — so a run whose only failures are the ~37 environment flakes (CET-8234/8424) is GREEN and the android rebase lane is no longer permanently red. Every suppression is printed verbatim.
6. **Comments stage**: if any `ACT` thread → run the `/resolve-pr-comments` procedure (classify FIX/REPLY/STALE/DEFER, apply fixes, post English replies, combined commit; strategy table auto-approved under `--auto`). Its build-sanity gate (format + check-test) still runs — and is the second abort `--auto` does NOT bypass, by design: check-test fails after FIX edits → STOP this PR with `needs-human: comment-fix-failed-tests`, push NOTHING (not even the rebase commit), leave the worktree dirty for inspection. Under `--auto` the skill also suppresses DEFER promise-replies ("will file a ticket after merge" — nobody in the loop files it; owner decision D16).
7. **Push — a NAMED terminal stage the worker ALWAYS owns, identical in both modes (GGC-91; supersedes the D14/V2-A orchestrator-hoist).** A rebase rewrote history, so every push is `--force-with-lease`. The push is the unit's final, explicitly-numbered stage: it runs to completion **before the worker emits its step-8 report**, exactly like `/dev:ship` is a named stage the dispatcher's workers never drop ("a named stage = unmissable"). There is NO orchestrator-owned push and NO rebase-only "hand the sha back to the caller" path — single mode and batch mode push the same way. It happens in one of two ways depending on whether comments ran:
   - **Comments stage ran** → `/resolve-pr-comments`'s own push step already executed the single `--force-with-lease` push (it must — the push has to follow its comment-fix commit, which only it knows is final). The Push stage sees `pushedSha` already set and is a no-op.
   - **Rebase-only (no comments stage)** → the **worker itself** runs the single `git push --force-with-lease=<headRefName>:<old_remote_sha>` after asserting `behind_after == 0 && tree_clean && rebased_sha present`, then records `pushedSha`. (`old_remote_sha` is the remote tip the worker reset to in step 4's stale-reuse refresh, so the explicit-lease form is exactly right.)
   **Why the worker can own this now (the 2026-06-08 retro had 1/9 workers drop the push):** the fix is the **named-stage structure, not prose**. The earlier remedy (V2-A) hoisted the push to the orchestrator because an orphan push step *after* `/resolve-conflict --callee` signals "done" is a structural trap — but hoisting bought reliability at the cost of a single/batch fork (two different endings for "the unit both modes run"). GGC-91 keeps the structural fix and drops the fork: the push is no longer an orphan tail, it is the unit's own numbered terminal stage that MUST complete before the report is emitted (the same mechanism that makes `/dev:ship` unmissable). A rebase-only worker that returns a report **without** `pushedSha` is a defect, not an accepted variance.
   The branch is pushed **once** per pass — possibly carrying two commits (rebase + comment-fix) on the comments path. A lease rejection (someone pushed between the worker's fetch and the push) → report `push-failed`, do NOT plain-force, and reset the worktree to `origin/<headRefName>` (discard the local commits) so the next pass re-rebases from remote reality instead of stacking on abandoned local commits.
8. **Report** (exit shapes):
   - `{pr#, skipped: up-to-date}` | `{pr#, skipped: judged-clean, held: [...]}`
   - **Rebase-only (no comments):** `{pr#, rebased: yes, rebased_sha, old_remote_sha, behind_after, tree_clean, comments: null, pushedSha, assumptions: [...]}` — the worker pushed in its own step-7 Push stage and reports `pushedSha`; the orchestrator only aggregates. (`old_remote_sha` / `behind_after` / `tree_clean` are retained for auditability — they are the lease inputs the worker asserted before pushing.)
   - **Comments path:** `{pr#, rebased: yes/no, comments: {fix, reply, stale, defer}, held: [...], resolvedThreadIds: [], pushedSha, assumptions: [...]}` (resolve-pr-comments already pushed).
   - **needs-human:** `needs-human: conflict | tests-failed | worktree-dirty | comment-fix-failed-tests | push-failed`. For `worktree-dirty`, ALWAYS include the non-residue file list **and** a one-paste recovery hint (V2-D): `cd <wt> && git diff` to inspect, `git -C <wt> stash` to clear (or re-run with `--stash-dirty`) — so the human can act without spelunking for the path.
   - **`assumptions` (GGC-15)** is the Tier-1 auto-assume ledger forwarded from the callee's Step 6 report (`resolve-conflict.md` Callee Mode) — every documented best-effort assumption made while auto-resolving a non-trivial conflict, each as `{file, region, assumption, heuristic}`. Empty / `[]` when the rebase was clean. The run report renders it (one block per PR that made assumptions) so the human sees what was assumed without opening each ticket; it is also posted to the PR's tracker ticket (or PR comment fallback) in step 5.
   `up-to-date` / `judged-clean` / `pushedSha` / `rebased_sha` / `assumptions` are stable field names — callers (e.g. /ggx-on-duty) key off them; do not rename.

## Batch mode

- **Top-level sweep (in THIS session — the bounded, non-blocking part).** `gh pr list --state open [--author @me]` → candidate PRs `{number, headRefName, baseRef}`. Apply the skip-set and the cheap pre-spawn filters (both below) to drop un-actionable PRs with **zero agents**, producing two lists: a `roster` of spawn-worthy PRs `{pr, headRefName, baseRef, ticketId}` and a `prefiltered` list (merged/closed/dirty PRs — reported, never spawned). This sweep is the only inline work the caller does; the per-PR units run inside the Workflow.
- **Fan-out via the `Workflow` tool (GGC-92), NOT N×Agent.** Invoke `workflows/pr-resolver-batch.workflow.js`, which pipelines the single-PR unit (the "Per-PR procedure" above, GGC-91) — one **script-spawned level-1 agent** per PR — in waves that hold the concurrency cap. Same fan-out mechanism the dispatcher uses (`workflows/dispatch-fanout.workflow.js`), so the platform has ONE fan-out path. The resolver unit is a **leaf** (`/resolve-conflict --callee` is inline, tests run in the worker foreground, the thread judge runs in the worker), so it never needs a level-2 spawn — Workflow fits with zero workarounds (Workflow-spawned agents have no Agent tool, GGC-90, but the unit never spawns).
  ```
  Workflow({
    name: "pr-resolver-batch",
    args: { roster, prefiltered, platform: <resolved profile platform>,
            stashDirty: <true iff --stash-dirty>, waveSize: 4 },
  })
  ```
  - **Fail-fast, no silent fallback (AC6).** If the `Workflow` tool call itself errors or the tool is unavailable, mirror the dispatcher's §5.2 invocation-error branch: report the error and STOP the batch — do **not** fall back to the retired N×Agent fan-out. Reversibility: this migration is a single commit; `git revert` restores the Agent-tool path.
  - The Workflow returns `{ counts, rows, prefiltered }` (plus `error` on a roster-parse / toolchain abort). Aggregate `rows` exactly as before (below); surface `error` as a batch failure.
- **Toolchain resolved ONCE inside the Workflow, injected by the script (P1-3 / P-B).** The fvm-aware `FLUTTER_BIN` is resolved by the Workflow's single `preflight` agent stage — a script can't run shell, so it MUST be an agent stage, not inline JS (same probe as `ui-tweak/start.md`'s resolved-env block) — and the SCRIPT injects the literal string into every per-PR unit prompt. Doing the inject in the script (rather than threading it markdown→args→prompt) is the structural P-B fix: the hand-off can no longer be silently dropped the way the 2026-06-08 retro's prompts dropped it (all 9 workers re-probed fvm and split system **3.41.6** vs fvm-pinned **3.38.7**). Each unit's spec forbids re-probing — *"use the `FLUTTER_BIN` handed to you for every flutter/dart/`/check-test` invocation; do NOT run `fvm`, `command -v`, or any probe."* If the repo pins its SDK (`.fvmrc` / `.fvm/fvm_config.json`) but fvm can't run it, the preflight agent returns `failFast` and the Workflow refuses to start ANY unit (a per-worker fallback is forbidden). flutter-only; android/ios/prompt repos skip the probe (`flutterBin=""`).
- **Pre-spawn filter: cheap top-level reads that drop un-actionable PRs BEFORE a worker is spawned (P0-2).** Steps 1 (MERGED/CLOSED) and 4 (dirty-worktree guard) already protect correctness, but only AFTER paying for a spawn (2026-06-08: #480/#500/#502 spawned then aborted dirty; #501 spawned, rebased + tested, only then discovered merged mid-run). In the top-level sweep, next to 3a, add for each candidate branch:
  - **Already merged/closed:** re-run `gh pr view <n> --json state -q .state` right before spawning; `MERGED`/`CLOSED` → skip with zero agents (a `gh pr list --state open` snapshot goes stale during a long batch).
  - **Dirty worktree:** if a worktree exists, `CHANGED=$(git -C <wt> diff --name-only HEAD)`; split against the residue allowlist `RESIDUE_RE='^(pubspec\.lock|ios/Podfile\.lock|Gemfile\.lock|ios/Flutter/AppFrameworkInfo\.plist)$'` (keep in sync with step 4 and `ggx-dispatcher.md`). Any file outside the allowlist → mark `needs-human: worktree-dirty` and do NOT spawn (the in-worker step-4 guard stays as the second line of defence for worktrees created during the batch).
  - Acceptance: dirty/merged PRs appear in the report with **zero** agents spawned.
- **Concurrency cap (P1-2) — enforced by the Workflow's waves, NOT its default cap.** At most **4–5 per-PR units run simultaneously**. Workflow's default cap is `min(16, cores−2)` — too high (13 full suites in parallel thrashed the CPU last run; one suite took ~33 min vs its usual few minutes). `pr-resolver-batch.workflow.js` therefore chunks the roster into **waves of `waveSize` (default 4)** and `parallel()`s each wave — it does NOT pass the whole roster to one `pipeline()`/`parallel()` call (that would inherit the high default cap). The cap + the strict-incremental rebase-stage tests (step 5) together keep wall-clock bounded.
- **Workers own their push (GGC-91; supersedes the V2-A orchestrator-push).** Every per-PR worker pushes inside its own named step-7 Push stage and returns `pushedSha` — on BOTH the rebase-only and comments paths. The orchestrator does **not** push; it only aggregates each worker's returned `pushedSha` / `assumptions` into the run report. A worker that reports a rebase-only result without `pushedSha` is surfaced as a defect (not silently re-pushed by the orchestrator). A worker's own lease rejection comes back as `push-failed` (the worker does not plain-force); the orchestrator surfaces it and moves on. This removes the single/batch push fork — the named-stage structure, not orchestrator ownership, is what closed the 1/9 missed-push variance (see step 7).
- **needs-human notification dedup (V2-D).** A `needs-human: worktree-dirty` PR will recur every loop iteration until the human clears it — re-announcing it loudly each run is noise (2026-06-08: #480/#499 re-flagged across 3 iterations). Persist the last-reported set to `claude-reports/ggx-pr-resolver/needs-human-state.json` (sibling to the cross-run report log already written there) as `{<headRefName>: <sha256 of the sorted non-residue file list>}`. On each run, a `needs-human` PR whose `(branch, fileset-hash)` is byte-identical to the stored entry is listed **compactly** ("unchanged since <prior run>") and NOT re-escalated to the notification layer; only a new PR, or one whose dirty fileset changed, fires a fresh loud notification. (`--stash-dirty` sidesteps this entirely by clearing the dirty state.) Pure notification hygiene — the dirty guard itself is unchanged and still correctly refuses to touch the worktree.
- Aggregate the per-PR reports; list `needs-human` PRs prominently. For every PR whose `assumptions` ledger is non-empty (GGC-15), render a short "Auto-assumed conflicts" block in the run report (PR# · ticket · the assumptions made) so a reviewer can audit the unattended merge decisions in one place — mirroring what step 5 already posted to each PR's tracker ticket.
- Skip-set: callers may pass a set of **branch names (headRefName)** to exclude — the canonical key (owner decision D11; PR numbers cannot work: chain-in-flight tickets may have no PR yet). E.g. /ggx-on-duty passes the dispatcher chain's claimed branches (E-3). Checked against `headRefName` from `gh pr list` in the top-level sweep BEFORE a branch enters the `roster` passed to the Workflow (so a skipped branch is never handed to a unit).

## Why one command instead of two

`/resolve-conflict --batch` and `/resolve-pr-comments` are the same category of work — writers to the same PR branch keeping it healthy. Run separately they need mutual-exclusion bookkeeping and push twice (two CI runs). Chained per-PR: rebase first means comment fixes are authored on top of latest base, one push (possibly two commits), one CI run, zero self-racing. A PR needing both stages runs the local suite twice (rebase stage + the skill's build-sanity gate) — deliberate (owner decision D17): the second run is incremental and the simplicity beats conditional skipping.
