# `/ui-tweak` 使用指南（給 UI Designer）

> 這份指南教你怎麼用 `/ui-tweak`、它的安全保護在哪裡、出問題時怎麼自救。
> 主要寫給 **UI Designer（不寫程式也看得懂）**，次要給維護這個 skill 的工程師。

---

## 1. 這是什麼 / 能做什麼、不能做什麼

**一句話定位**：你用一句話（或一張 Figma、一張 ticket）描述一個 UI 調整，Claude 幫你在程式碼裡改好「純畫面」的部分。你想看的時候，它會把改好的 App **裝進一台裝置（模擬器或你接著的手機）讓你親眼看**；你覺得 OK 了，它再幫你開一個 **draft PR** 讓工程師 review。

**能做（視覺 / 版面 / 結構 的 UI 改動）：**
- 改數值：間距、padding、margin、圓角、字級、字重、顏色、透明度、陰影、元件大小等。
- 改版面 / 結構：調整排列、把區塊上下對調、新增或移除畫面上的 UI 元素、換容器、改對齊方式。
- 對齊 Figma：照著 Figma 上標的數值去改。

**不能做（會被擋下來）：**
- 改邏輯：例如金額計算、條件判斷、按鈕按下去「做什麼事」、資料怎麼存取、頁面要跳去哪。
- 改 build 設定 / 專案設定：例如 `build.gradle`、`pubspec.yaml`、`AndroidManifest.xml`、`Info.plist` 等。

**它會做、但你不用碰的：** 編譯、把 App 裝進裝置、commit、開 draft PR——這些它在對的時機自動做。**它不會自動 merge、不會把 draft PR 轉成 ready、不會改 ticket 狀態。**

> ⚠️ 關於「看畫面」：它只負責把 App **裝好、開起來**在裝置上，然後**把裝置交給你**——它**不會幫你截圖、不會幫你點來點去、不會幫你授權或導航到某個畫面**。你自己看、自己操作到要看的那一頁。唯一的例外是送出時可以選「**Ship it — 順便錄一段 demo**」：在你確認過畫面**之後**，它會把螢幕上當下的畫面錄下來放進 PR（依然零點擊、零導航，而且你完全不用等它）。

---

## 2. 前置需求（第一次用之前先確認）

1. **要先跑過 `install.sh`**：這支安裝程式會把 skill / 指令 / agent 連結進 Claude Code。**它不再安裝任何 hook，也不會在你的設定檔（`~/.claude/settings.json`）留下「守門員」**——安全把關改由「編譯（Phase 1）＋雙評審（Phase 2）」在你按下「Ship it」送出前完成（見下方〈保證〉）。
2. **要在「實際的 App 專案資料夾」裡用**，不是在這個工具 repo 裡用。也就是要在 Android / Flutter / iOS 的程式碼專案裡——這個專案根目錄要有一個 `.gogox-claude.yaml` 檔（用來告訴 skill 這是哪個平台、用什麼指令編譯與裝進裝置）。
3. **想在裝置上看畫面**：要嘛有一台模擬器 / 模擬機可以開，要嘛先把實體手機接上。都沒有也沒關係——它會誠實告訴你「找不到裝置可以顯示，但我確認它能正常編譯」，由你決定要不要直接送出。

---

## 3. 怎麼用

指令格式：

```
/ui-tweak <source> [figma-url]
```

`<source>`（來源）可以是三種，skill 會自動辨認是哪一種：

**A. 自由文字**（直接講你要改什麼）
```
/ui-tweak 把訂單頁的 button 高度調大 5dp
```

**B. Linear / Jira ticket（ticket 編號或網址）** — 通常是最完整的來源，因為 ticket 常常已經寫好要改哪個畫面、哪個元件、改成多少，還可能附了 Figma 連結。
```
/ui-tweak CAF-1234
```
> ticket 是**唯讀**的：skill 只會「讀」ticket 內容，不會改 ticket 狀態、不會指派、不會留言。例外只有兩個：你選擇送出後，它會在 ticket 上**貼一則 draft PR 的連結**；如果你有交給它截圖／錄影（或請它錄了 demo），它會把**那個檔案附到 ticket 上**（這樣 PR 裡才能顯示）。兩者都不會動到狀態或指派。

**C. Figma 連結**（照設計稿改）
```
/ui-tweak 訂單頁 button 對齊設計稿 https://figma.com/design/....?node-id=...
```

最後那個 `[figma-url]` 是選填的：當你想讓 skill 讀 Figma 上的精確數值時加上它；如果是純文字、或 ticket 裡已經有正確的 Figma 連結，就可以省略。

> **工作項目編號一定要有。** A、C 兩種寫法仍然可用，但如果你的輸入沒帶編號（像 `CAF-1234`），skill 會在開始前先問你要一個 —— 每個改動都會掛在某個工作項目底下、之後才能交給工程師。最快的方式是用 B（直接從 ticket 開始），或在文字裡帶上編號。

## 4. 執行時會發生什麼（流程白話版 — 兩階段）

你全程只會看到「**白話卡片**」，照著選號碼或直接用一句話回覆就好。背後分兩個階段：

**前置設定（自動、無聲）**
0. 在動任何東西之前，它會先把你的改動放進**一個專屬的獨立空間**，跟其他人的工作分開，所以你在這裡做什麼都不會影響到團隊現有的程式。如果你的需求已經帶了工作項目編號（像 `CAF-1234`）就直接用；如果你是用純文字開始、沒有編號，它會在最一開始問你一次：「**這個的工作項目編號是多少？**」—— **一定要有編號**（每個改動都會掛在某個工作項目底下，之後才能交給工程師）。沒有的話，請先去建一個、或跟你的 PM／工程師要，再用那個編號重新跑一次 `/ui-tweak`。整個設定你都不用自己處理。

**反覆調整（免費、很快）**
1. **解析來源 + 改 code**：看你給的是文字、ticket 還是 Figma，整理出「要改什麼」，列一張「改哪些檔、現在的值 → 要改成的值」的表給你確認，然後只改畫面相關的部分。**這個階段不編譯**，所以你想改幾次就改幾次，很快。
2. **問你**：「我改好了 → **給我看 / 直接送出 / 還要修改**」。要再調就直接講（例如「再大一點」「往下移一格」），它疊加修改；不用花時間等編譯。**如果你已經自己在裝置上看過了**，可以選「**看起來沒問題 — 直接送出**」：它會跳過手機預覽，快速確認最新的改動仍然能正常運作，然後直接進入最終檢查與交付（你自己 build 的版本可能是改動前的，所以這個快速確認一定會跑）。

**階段一：給你看（你說「我改好了」才會跑）**
3. 它把改好的 App **編譯 + 裝進一台裝置並開起來**（優先用你已接上的實體手機或已經開著的模擬器；沒有才現場開一台；都沒有就退化成「只確認能編譯」並誠實告訴你）。從你開始這次任務的那一刻起，它就會在背景先悄悄暖機一台模擬器，所以這一步通常不用等慢吞吞的冷開機。
4. **App 一開起來，它就停手，把裝置交給你**——你自己看、自己點到要看的那一頁。它不截圖、不幫你操作。
5. 然後問你：「**看起來對嗎？ → Ship it（送出）/ Ship it — 順便錄一段 demo / 還要修改**」。選「**順便錄一段 demo**」它會把螢幕上當下的畫面（就是你剛確認過的那一頁）錄下來放進 PR——錄製發生在你按完**之後**，你完全不用等；它依然不會幫你點擊或導航。如果你自己有截圖或錄影，也可以直接交給它（貼上 / 拖進來）——它會附在 PR 裡，讓工程師看到實際的結果。

**階段二：送出（你說「Ship it」才會跑）**
6. 它跑**完整的邏輯把關**（獨立 AI 稽核，確認只動了畫面、沒動到程式運作），通過後**自動 commit、開一個 draft PR**，並在 ticket 上留連結。PR 裡會帶上所有已經存在的視覺素材——ticket 上的設計圖 / Figma 連結、你交給它的截圖、以及你請它錄的 demo（如果有）——讓工程師知道要對照什麼（除了那個你主動選的 demo 之外，skill 不會自己捕捉任何畫面）。
7. 完成——你的部分結束。draft PR 不會自動上線，由工程師做最後 review。

**如果編譯或邏輯把關失敗了？**
你**不會**看到一堆編譯錯誤。它會把這當成「實作出了問題」，**自己回去修（最多 3 次）**；如果修了 3 次還是不行（通常代表這個改動其實需要動到程式運作、不只是外觀），它才會跟你說「**這部分建議找工程師**」。

## 5. 安全保證（白話版）

這個 skill 的設計目標是：**讓設計師「不小心」改壞邏輯這件事很難發生。** 它**沒有編輯期守門員**——把關延後到送出前的兩道檢查:

- **編譯（階段一）** 在你說「給我看」時跑,編不過就還原。
- **兩位獨立 AI 稽核員（不同視角，階段二）** 在你說「Ship it」、開 PR 之前跑**一次**,讀整份改動判斷有沒有動到邏輯;**兩位都要通過——只要有一位判定動到邏輯(不管是不該動的非 UI 檔、還是 UI 檔內部被改了邏輯),整筆改動就會被退回讓 agent 重做,不會偷偷送出。** 因為沒有任何上游證明這份改動只動數值,所以**兩位稽核員每次都會跑**,不會省略。

> 為什麼把邏輯把關放到最後一次？因為你在反覆調整時不需要每次都燒一次 AI 稽核——把關放在「真正要送出去之前」做一次最划算,而且審的是最終會送出的版本。反覆調整期間的工作樹是**未經稽核**的——稽核員是送出那一關的安全網,不是編輯當下。

**一句話總結：**「沒動到邏輯」這條是**盡力而為**——靠送出前的雙 AI 稽核 ＋ 編譯把關,不是物理上不可能,所以**你還是只該做 UI 改動**。

## 6. 哪些會被擋（範例）

下面這些會被擋住、skill 會停手並告訴你原因：

- **改 ViewModel / Repository**：例如要改的值只存在某個 `OrderViewModel.kt` 的常數裡——這不是純 UI 改動，會被擋，skill 會請你走工程流程。
- **改金額計算邏輯**：例如 `if (user.isPremium) price = base * 0.8`——這是計算行為，會被擋。
- **加一個會呼叫函式的 onClick**：例如把按鈕的點擊行為改成呼叫一個新函式、或新增一個會做事的點擊事件——這是行為（邏輯），不是樣式，會被擋。
- **改 build / 專案設定**：動到 `build.gradle`、`pubspec.yaml`、`Info.plist`、`AndroidManifest.xml` 等，會被擋。
- **改程式會參照的 id / 函式名稱**：例如改掉某個被程式碼引用的 `@+id/...` 或函式名，可能會讓程式找不到東西，會被擋。

## 7. 限制與已知弱點

- **Flutter / SwiftUI / Compose 混合檔最難分辨**：這些框架的畫面和邏輯混在同一個檔、用同樣語法，沒有靜態規則能完美區分「UI vs 邏輯」。
- 因為**沒有編輯期守門員**，保證是**「送出前雙稽核＋編譯」等級**,不是物理級的不可能。也就是說它防的是**「不小心改壞」**,不是防一個刻意想繞過保護的人。
- **看畫面需要裝置**：沒有模擬器 / 實體機時，它只能確認「能編譯」，沒辦法給你看畫面——這時要嘛接一台裝置再來一次，要嘛直接送出讓工程師看。
- Android 是最乾淨的情況（資源檔分得清楚）；Flutter / SwiftUI 的改動最好落在 theme / token 檔裡，或限於 widget 檔裡單純換數值 / 換顏色。

---

## 8. 疑難排解

**「給我看」時開不了裝置 / 一直找不到裝置**
- 它會依序嘗試：用你已接上 / 已經開著的裝置（含實體機）→ 開一台模擬器 / 模擬機 → 都沒有就退化成「只確認能編譯」。
- 如果你想在實體機上看，先確認手機已用 USB / wifi 連上（`flutter devices` 看得到），再跑「給我看」。
- 最快的方式是讓模擬器 / 模擬機在兩次操作之間保持開著——已經開著的裝置會被直接選用、完全不用等開機（每次新任務開始時它也會在背景先暖機一台）。

**skill 的說明（description）顯示異常 / skill 沒被認出來**
- 原因通常是 `SKILL.md` 的 frontmatter（檔案最上面那段 `---` 包起來的設定）沒放在**第一行**。
- 解法：確認 `SKILL.md` 第一行就是 `---`，frontmatter 必須在檔案最開頭。

---

## 9. 終點是哪裡（重要）

`/ui-tweak` 的終點鎖在 **draft PR**，而且**只在你親手選「Ship it」時才會走到那裡**：

- 反覆調整、或選「給我看」→ 都不會送出任何東西，改動只留在你的工作目錄。
- 選「Ship it」→ 邏輯把關 → commit → 開 **draft PR**（PR 的 Demo 區會帶上 ticket 的設計圖、你交的截圖、你請它錄的 demo——如果有）+ 在 ticket 留連結。
- **它永遠不會自動 merge、不會把 draft 轉成 ready、不會改 ticket 狀態。** 人工 review 那關是刻意保留的——因為沒有編輯期 hook，「沒動到邏輯」是靠編譯＋雙評審在送出前盡力把關，最後仍必須由人在 PR 上確認。
