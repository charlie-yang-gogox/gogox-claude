# `/ui-tweak` 使用指南（給 UI Designer）

> 這份指南教你怎麼用 `/ui-tweak`、它的安全保護在哪裡、出問題時怎麼自救。
> 主要寫給 **UI Designer（不寫程式也看得懂）**，次要給維護這個 skill 的工程師。

---

## 1. 這是什麼 / 能做什麼、不能做什麼

**一句話定位**：你用一句話（或一張 Figma、一張 ticket）描述一個 UI 調整，Claude 幫你在程式碼裡改好「純畫面」的部分。你想看的時候，它會把改好的 App **裝進一台裝置（模擬器或你接著的手機）讓你親眼看**；你覺得 OK 了，它再幫你整理成一份「給工程師的提案（draft PR）」。

**能做（視覺 / 版面 / 結構 的 UI 改動）：**
- 改數值：間距、padding、margin、圓角、字級、字重、顏色、透明度、陰影、元件大小等。
- 改版面 / 結構：調整排列、把區塊上下對調、新增或移除畫面上的 UI 元素、換容器、改對齊方式。
- 對齊 Figma：照著 Figma 上標的數值去改。

**不能做（會被擋下來）：**
- 改邏輯：例如金額計算、條件判斷、按鈕按下去「做什麼事」、資料怎麼存取、頁面要跳去哪。
- 改 build 設定 / 專案設定：例如 `build.gradle`、`pubspec.yaml`、`AndroidManifest.xml`、`Info.plist` 等。

**它會做、但你不用碰的：** 編譯、把 App 裝進裝置、commit、開 draft PR——這些它在對的時機自動做。**它不會自動 merge、不會把 draft PR 轉成 ready、不會改 ticket 狀態。**

> ⚠️ 關於「看畫面」：它只負責把 App **裝好、開起來**在裝置上，然後**把裝置交給你**——它**不會幫你截圖、不會幫你點來點去、不會幫你授權或導航到某個畫面**。你自己看、自己操作到要看的那一頁。

---

## 2. 前置需求（第一次用之前先確認）

1. **要先跑過 `install.sh`**：這支安裝程式會把一個「守門員」程式（hook）登記到 Claude Code 的設定檔 `~/.claude/settings.json` 裡。沒有它，這個 skill 會**拒絕動工**（因為少了硬性保護）。
2. **登記完 hook 之後，要「重啟 Claude Code session」才會生效**：hook 是在 session 啟動時被讀進去的，剛裝好但沒重啟，等於還沒生效。
3. **要在「實際的 App 專案資料夾」裡用**，不是在這個工具 repo 裡用。也就是要在 Android / Flutter / iOS 的程式碼專案裡——這個專案根目錄要有一個 `.gogox-claude.yaml` 檔（用來告訴 skill 這是哪個平台、用什麼指令編譯與裝進裝置）。
4. **想在裝置上看畫面**：要嘛有一台模擬器 / 模擬機可以開，要嘛先把實體手機接上。都沒有也沒關係——它會誠實告訴你「找不到裝置可以顯示，但我確認它能正常編譯」，由你決定要不要直接送出。

> 小提醒：hook、守門員、guard 講的都是同一個東西——一個會在 Claude 每次要改檔案前先檢查、擋下不該改的東西的小程式。

## 3. 怎麼用

指令格式：

```
/ui-tweak <source> [figma-url]
```

`<source>`（來源）可以是三種，skill 會自動辨認是哪一種：

**A. 自由文字**（直接講你要改什麼）
```
/ui-tweak 把訂單頁的 button 高度調大 5dp
```

**B. Linear / Jira ticket（ticket 編號或網址）** — 通常是最完整的來源，因為 ticket 常常已經寫好要改哪個畫面、哪個元件、改成多少，還可能附了 Figma 連結。
```
/ui-tweak CAF-1234
```
> ticket 是**唯讀**的：skill 只會「讀」ticket 內容，不會改 ticket 狀態、不會指派、不會留言。唯一的例外是你選擇送出後，它會在 ticket 上**貼一則 draft PR 的連結**（唯讀通知，不改狀態）。

**C. Figma 連結**（照設計稿改）
```
/ui-tweak 訂單頁 button 對齊設計稿 https://figma.com/design/....?node-id=...
```

最後那個 `[figma-url]` 是選填的：當你想讓 skill 讀 Figma 上的精確數值時加上它；如果是純文字、或 ticket 裡已經有正確的 Figma 連結，就可以省略。

## 4. 執行時會發生什麼（流程白話版 — 兩階段）

你全程只會看到「**白話卡片**」，照著選號碼或直接用一句話回覆就好。背後分兩個階段：

**反覆調整（免費、很快）**
1. **解析來源 + 改 code**：看你給的是文字、ticket 還是 Figma，整理出「要改什麼」，列一張「改哪些檔、現在的值 → 要改成的值」的表給你確認，然後只改畫面相關的部分。**這個階段不編譯**，所以你想改幾次就改幾次，很快。
2. **問你**：「我改好了 → **給我看 / 還要修改**」。要再調就直接講（例如「再大一點」「往下移一格」），它疊加修改；不用花時間等編譯。

**階段一：給你看（你說「我改好了」才會跑）**
3. 它把改好的 App **編譯 + 裝進一台裝置並開起來**（模擬器 / 模擬機，或你接著的實體手機；都沒有就退化成「只確認能編譯」並誠實告訴你）。
4. **App 一開起來，它就停手，把裝置交給你**——你自己看、自己點到要看的那一頁。它不截圖、不幫你操作。
5. 然後問你：「**看起來對嗎？ → Ship it（送出）/ 還要修改**」。

**階段二：送出（你說「Ship it」才會跑）**
6. 它跑**完整的邏輯把關**（獨立 AI 稽核，確認只動了畫面、沒動到程式運作），通過後**自動 commit、開一個 draft PR**，並在 ticket 上留連結。
7. 完成——你的部分結束。draft PR 不會自動上線，由工程師做最後 review。

**如果編譯或邏輯把關失敗了？**
你**不會**看到一堆編譯錯誤。它會把這當成「實作出了問題」，**自己回去修（最多 3 次）**；如果修了 3 次還是不行（通常代表這個改動其實需要動到程式運作、不只是外觀），它才會跟你說「**這部分建議找工程師**」。

## 5. 安全保證（白話版，分兩層 ＋ 兩個時間點）

這個 skill 的設計目標是：**讓設計師「不小心」改壞邏輯這件事不會發生。** 保護分兩層強度：

**第一層：硬保證（鐵打的，不靠 AI 判斷）**
- 它**絕對碰不到非 UI 檔**：像 ViewModel、Repository、資料層、網路層、DI、build 設定、manifest、測試、自動產生的檔案等，這些檔案在改 code 期間是**物理上改不了**的。
- 在「改 code 的那段期間」，**完全不能執行任何終端機（Bash）指令**——因為 build 工具本身就是能跑任意程式的引擎，沒有「安全的指令白名單」這種東西，所以乾脆全部封鎖。

**第二層：盡力而為（best-effort，靠 AI ＋ 編譯把關）**— 在不同時間點跑：
- **編譯**在你說「給我看」時跑（階段一），編不過就還原。
- **獨立 AI 稽核員（兩位、不同視角）** 在你說「Ship it」時、開 PR 之前跑**一次**，讀整份改動判斷有沒有動到邏輯；**任一位判定動到邏輯，整筆改動就會被退回讓 agent 重做（不會偷偷送出）**。

> 為什麼把邏輯把關放到最後一次？因為你在反覆調整時不需要每次都燒一次 AI 稽核——把關放在「真正要送出去之前」做一次最划算，而且審的是最終會送出的版本。在**預設的 strict 模式**下，反覆調整期間的工作樹本來就被守門員鎖成「只能改數值」，所以中途不審也是安全的。

**一句話總結：**
鐵打的是「碰不到非 UI 檔」＋「改 code 期間不能跑終端機指令」。
而「UI 檔案內部沒動到邏輯」這條是**盡力而為**——靠送出前的 AI 稽核 ＋ 編譯把關，不是物理上不可能，所以**你還是只該做 UI 改動**。

## 6. strict vs open 兩種模式

| 模式 | 允許什麼 | 怎麼把關 | 何時用 |
|---|---|---|---|
| **strict（給設計師的預設）** | 只准「視覺數值」改動、或「純粹重排」（同樣的行只是換順序） | 守門員在字元層級硬性檢查，只放行視覺數值（改 code 當下就鎖死，不靠 AI） | 設計師日常用。最保險，寧可被多擋也不放錯 |
| **open（power-user / 各 repo 自行開啟）** | 任何「UI 形式」的改動：改數值、改版面、重排、新增/移除 UI 元素 | 守門員只擋「非 UI 檔」；UI 檔內部完全靠送出前的 AI 稽核 ＋ 編譯把關 | 要做較大結構性調整、且接受「工作樹在送出前未經 AI 稽核」的人 |

簡單記：**設計師預設 strict（最保險，只動數字 / 純重排）。** strict 會擋掉一些其實合理的結構性 UI 改動，這是它換取確定性的代價——被擋到時，改用 open 是各 repo / power-user 的選擇，不是預設。

## 7. 哪些會被擋（範例）

下面這些會被擋住、skill 會停手並告訴你原因：

- **改 ViewModel / Repository**：例如要改的值只存在某個 `OrderViewModel.kt` 的常數裡——這不是純 UI 改動，會被擋，skill 會請你走工程流程。
- **改金額計算邏輯**：例如 `if (user.isPremium) price = base * 0.8`——這是計算行為，會被擋。
- **加一個會呼叫函式的 onClick**：例如把按鈕的點擊行為改成呼叫一個新函式、或新增一個會做事的點擊事件——這是行為（邏輯），不是樣式，會被擋。
- **改 build / 專案設定**：動到 `build.gradle`、`pubspec.yaml`、`Info.plist`、`AndroidManifest.xml` 等，會被擋。
- **改程式會參照的 id / 函式名稱**：例如改掉某個被程式碼引用的 `@+id/...` 或函式名，可能會讓程式找不到東西，會被擋。

## 8. 限制與已知弱點

- **Flutter / SwiftUI / Compose 混合檔最難分辨**：這些框架的畫面和邏輯混在同一個檔、用同樣語法，沒有靜態規則能完美區分「UI vs 邏輯」。
- 所以在 **open 模式下，UI 檔案內部的保證是「送出前審查＋編譯」等級**，不是物理級的不可能。也就是說它防的是**「不小心改壞」**，不是防一個刻意想繞過保護的人。（strict 模式因為當下就鎖成只能改數值，沒有這個弱點。）
- **看畫面需要裝置**：沒有模擬器 / 實體機時，它只能確認「能編譯」，沒辦法給你看畫面——這時要嘛接一台裝置再來一次，要嘛直接送出讓工程師看。
- Android 是最乾淨的情況（資源檔分得清楚）；Flutter / SwiftUI 的改動最好落在 theme / token 檔裡，或限於 widget 檔裡單純換數值 / 換顏色。

---

## 9. 疑難排解

**最重要一條：上次中途中斷，導致這次任何指令都被擋**
- 原因：skill 在改 code 期間會放一個「武裝中」的標記檔（叫 sentinel）。如果上一次跑到一半被中斷（當機、Ctrl-C、context 重置），這個標記檔會殘留在「武裝」狀態，於是下一次連最簡單的指令都會被守門員擋住。
- 正常情況：重新跑 `/ui-tweak`，它的第一步會自己偵測並解除這個殘留標記。
- 手動解法（卡住時直接用）：刪掉那個標記檔即可。
  ```
  rm <專案根目錄>/.dev/ui-designer-mode.json
  ```

**hook 沒生效？（改動沒被擋，或 skill 說 guard MISSING）**
- 解法：**重跑 `install.sh`**，然後**重啟 Claude Code session**。
- 補充：hook 必須登記在 `~/.claude/settings.json`，不能放在 `settings.local.json`（後者會蓋過前者，造成「看起來裝好了、其實守門員沒啟動」的假象）。有疑慮就重跑 `install.sh` 並留意它的提醒。

**「給我看」時開不了裝置 / 一直找不到裝置**
- 它會依序嘗試：開一台模擬器 / 模擬機 → 用你已接上的裝置（含實體機）→ 都沒有就退化成「只確認能編譯」。
- 如果你想在實體機上看，先確認手機已用 USB / wifi 連上（`flutter devices` 看得到），再跑「給我看」。

**skill 的說明（description）顯示異常 / skill 沒被認出來**
- 原因通常是 `SKILL.md` 的 frontmatter（檔案最上面那段 `---` 包起來的設定）沒放在**第一行**。
- 解法：確認 `SKILL.md` 第一行就是 `---`，frontmatter 必須在檔案最開頭。

---

## 10. 終點是哪裡（重要）

`/ui-tweak` 的終點鎖在 **draft PR**，而且**只在你親手選「Ship it」時才會走到那裡**：

- 反覆調整、或選「給我看」→ 都不會送出任何東西，改動只留在你的工作目錄。
- 選「Ship it」→ 邏輯把關 → commit → 開 **draft PR** + 在 ticket 留連結。
- **它永遠不會自動 merge、不會把 draft 轉成 ready、不會改 ticket 狀態。** 人工 review 那關是刻意保留的——open 模式下「UI 檔內部沒動到邏輯」只是盡力而為的保證，必須由人在 PR 上做最後把關。
