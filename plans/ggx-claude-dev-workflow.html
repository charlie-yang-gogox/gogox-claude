gogox-claude 自身的 Linear → dev → PR 工作流程

把既有的 app-repo 開發 pipeline，改造成能開發「skills 倉庫本身」的架構規劃 · 2026-06-09

一句話：你要的流程（Linear → 確認完整度 → 確認相依 → 平行做 → PR）已經存在， 由 /ticket-analyze → /ggx-dispatcher → /ggx-work → /route → ff pipeline 組成。但它是為 flutter app repo（CAF/DAF team）設計的。要讓它跑在 gogox-claude 自己身上，缺三塊地基：(1) 這個 repo 沒有 profile、 (2) 「build / test / verify」對 prompt 倉庫沒有意義、(3) 你在修的正是 pipeline 自己（自我修改風險）。 本頁規劃如何補齊，並逐一對應現有 skill 哪些直接用、哪些要改、哪些跳過。

4要新建的地基（3 件）

① repo profile

放 <repo>/.gogox-claude.yaml（committed → co-owner 共用，符合 ARCHITECTURE.md「shared repo」精神）：

ticket_system: linear branch_prefix: GGC platform: prompt # 新 platform product: gogox-claude

② prompt platform profile

commands/dev/profiles/platform/prompt.yaml——因為 node.yaml 的 npm ci / npm test / eslint 本 repo 都沒有：

deps_install: "" # no-op test_cmd: ./scripts/prompt-lint.sh format_cmd: "" # 或 prettier --write '**/*.md' ide_open_hint: "open in VS Code"

③ prompt-lint 驗證腳本（取代「build」）

prompt 倉庫沒有編譯器，但有可機器檢查的東西。scripts/prompt-lint.sh 對「本次 diff 改到的檔」跑：

1. shellcheck — 抽出 .md 內嵌 ```bash 區塊做靜態檢查 ← 會擋 F1（macOS 無 timeout） 2. node --check workflows/*.js ← 語法錯立刻現形 3. bash -n install.sh ← 安裝腳本不破 4. frontmatter lint — 改到的 command/skill .md 有合法 name/description （ARCHITECTURE.md「待辦」清單裡的 SKILL.md 驗證，這裡順手補上）

注意：自動 lint 只能擋「語法 / 形狀」級的錯。prompt 真的有沒有照預期跑，唯一證明是 dogfood——見 §6。

OpenSpec 政策（建議拍板）

skill 編輯預設走 bug lane（/bug:ff），它原生跳過 OpenSpec。 GGC 票照 bug / feature 分類即可——大多數「修 prompt/bash」的票標 bug 就能吃到 OpenSpec-free 的最短路徑； 只有「設計一個全新 skill 行為」才值得走 /dev:ff 全套。

5相依 + 波次：套到 GGC-1~9

相依偵測優先讀 Linear 原生 blockedBy relations（文字推斷在 --non-interactive 下只當參考）。 目前 GGC 票只設了 parent/sub-issue（不是 blocking edge）→ 不設 relation 的話 analyze 會把它們全判獨立、全部平行。實際相依只有一條：

┌──────────────────────── 第 1 波（平行）────────────────────────┐ GGC-2 F1 ─┐ GGC-3 F2 GGC-5 D GGC-6 C GGC-7 B+ GGC-8 A2 GGC-9 E (timeout) │ (lock污染) (審查並行) (demo抓對頁) (flavor偵測) (HMR) (cursor) │ │ blockedBy（F1 沒修好 → iOS device 偵測壞 → 無法量測 iOS 啟動時間） ▼ GGC-4 Phase 1.5 iOS spike ───────────────── 第 2 波（GGC-2 的 PR merge 後解鎖）

於是波次自然成形：

  1. (一次性) 設 GGC-4 blockedBy GGC-2；其餘維持獨立。
  2. /ticket-analyze（GGC team）→ F1/F2/D/C/B+/A2/E 標 ready-to-dev，Phase 1.5 標 need-dependency。
  3. /ggx-dispatcher --team:GGC → 第 1 波 7 張票平行開 draft PR。
  4. 你 review + merge GGC-2 (F1) 的 PR → 重跑 /ticket-analyze → GGC-4 自動翻 ready-to-dev → 再 dispatch（第 2 波）。

6本 repo 獨有的兩個陷阱

⚠ 自我修改（self-modification）

你在修的檔（commands/dev/ggx-dispatcher.md、/dev:verify …）就是正在驅動這次工作的 pipeline 本身。兩件事保護你、一件事要小心：

  • ✓ worktree 隔離：agent 在 ../GGC-N 自己的 copy 改檔，不動 main worktree。
  • ✓ 執行用的是 installed 版：跑中的 orchestrator 讀 ~/.claude（symlink 到 main worktree），不讀 agent 的 worktree copy → 改 dispatcher 不會在半途改變正在跑的 dispatcher 行為。
  • ⚠ 但這也代表：改完的 skill 要「真的測」，必須先 install.sh（或把 ~/.claude 指向該 worktree）才生效。沒重裝＝你 review 的是新碼、跑的是舊碼。

⚠ dogfooding 需要一個「靶場」app repo

像 /ggx-dispatcher、/ui-tweak、/dev:ff 這種 skill，真正的驗收是拿它去跑一張真 app 票（F1 是在 CAF-609 上才現形的）。 所以本 repo 的「verify」是兩段：(a) prompt-lint（自動、擋語法/bash 陷阱）+ (b) dogfood（半人工、在 gogox-client-flutter 上跑一遍，HITL 確認後才 merge）。 建議把 (b) 設成 ship 前的人工 gate，而不是塞進 --auto。
